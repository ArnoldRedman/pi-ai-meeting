# 多模型会议

## 何时用 / 何时不用

**用**：判断题要多视角；我已有判断想被反驳；有 3–5 个互斥方案要选一个；稿件改了几轮需要"验收"（有没有引入新矛盾）；需要机制层面的挑错。

**不用**：事实查询（用 `web_search`）、代码实现（直接做）、只有一个合理答案的问题、需要真实读者数据的问题。

## 席位：读配置，不要写死

席位表在 pi 配置目录下的 `ai-meeting.json`，通常是 `~/.pi/agent/ai-meeting.json`（准确路径看 `/ai-meeting:config` 的输出）。

- **文件不存在**，或用户想换席位的模型 → **让用户运行 `/ai-meeting:config`**。它交互式地逐席选"供应商 → 模型 → 思考档位"，只列出真实可用、且该模型支持的档位；`/ai-meeting:config raw` 则直接用编辑器改 JSON。
- **绝对不要自己编模型 id**：不在注册表里的模型会让那个席位 0 秒硬失败。要列可选模型用 `pi --list-models`。
- 不要替用户改这个文件；它是用户自己的实测配置。

```json
{
  "version": 1,
  "seats": [
    { "provider": "anthropic", "model": "claude-opus-4", "thinking": "high", "name": "opus", "note": "结构最清，保守" }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `provider` / `model` | 必须是注册表里真实存在的组合；传给子会话时拼成 `provider/model:thinking` |
| `thinking` | 必须是该模型 `thinkingLevelMap` 里非 null 的档（交互式配置只会列合法档位） |
| `name` | 席位简称：用作子会话 key 和"谁改了什么主意"的标签，**必须唯一** |
| `note` | 只给人看的实测特点，不影响开会 |

- **3–5 席**合适。2 席只能互相对拍，6 席以上成本线性涨而边际收益掉。
- **席位之间必须真的是不同模型**：同一个模型挂在两个供应商名下只是重复，不算独立视角。
- 供应商的认证、可用模型清单都是用户本机的事，不要假设别的机器上有同样的模型。

### 怎么摸清各席位的脾气

开会前你不知道谁保守、谁爱改判。方法：拿一个**你自己已经有答案**的判断题开一次会（`cross: false` 就够），看谁敢推翻你、谁只是复述。把观察写进对应席位的 `note`。经验上值钱的特征有：敢不敢改判、会不会抓机制漏洞、静默思考多久、是否忽略格式约束。

## 三条硬规矩（违反必出事）

1. **换过模型后，先让用户在 pi 里按一次 `/model` 重载注册表**。否则该席位硬失败：`Unknown subagent model '...' in the active Pi model registry`。（硬失败比静默打到旧模型上强。）
2. **开会就是一次 `subagent` 调用，必须给 `timeoutMs`**，`runs.all` 会被最慢的席位绑架；单席位失败由脚本兜住，不许带崩整场。
3. **不许下"精确字数"约束**——实测有模型会起 `bash` + `python` 数字数，拖慢整场。写成"控制在 N 字左右，**不必精确，不要为此运行命令**"。

## 流程

1. **读配置 + 写问题单**（写法与六类会议模板见 `references/question-design.md`）：逼具体、给**机制契约**、允许它们反驳我、允许它们自己写一版。
2. **开会**——脚本是现成的，直接当脚本文件调用，不要复制代码进回复：

```js
subagent({
  workflow: "<本 skill 目录>/references/meeting.js",
  async: true,
  timeoutMs: 1800000,
  args: {
    seats: [ /* 原样粘贴 ai-meeting.json 里的 seats 数组，别改字段名 */ ],
    brief: "问题单全文（自包含）",
    cross: true,
    tag: "设定-0725"
  }
})
```

- `cross: true`：第一轮并行独立表态（`context: fresh`，互相隔离）**＋** 第二轮匿名交叉质询，一次跑完。审稿、机制挑错、方案选型用 `true`。
- `cross: false`：只跑第一轮，约省一半时间。只想快速取值、或问题本身没有分歧余地时用。
  门控靠这里：两种都在**启动前**决定；`cross: true` 时若第一轮高度一致，第二轮直接当没发生、不当依据即可。**不要为了补质询轮重跑第一轮。**
- `brief` 要自包含：席位是 fresh 上下文，没有你的上一轮。长材料**写绝对路径让它们自己 `read`**（`args` 上限 16 KiB）。
- 返回值里每个席位都带 `runId`（第一轮、第二轮各一个），后续轮次用它 `resume`——不要重跑第一轮。
- `async: true` 会先返回执据，完成才有返回值：**等到通知/返回值再汇总**，不要凭开会过程中的局部输出下结论。

3. **汇总**（做法见 `references/question-design.md`）：产出分三类——**真洞 / 我已知的取舍 / 空话**；**逐条自己回读原文验证**，不要当传声筒；把"**谁改了什么主意**"单列出来，那是最有信号的部分。

4. **后续轮**（投票、验收）都是**新开一场会**（fresh，选项/改后原文写进 `brief`），选项一律匿名，不告诉谁提的：
   - 投票轮：每席一票 + 一行理由 + **"如果我这票是少数，我接受哪个"**——这一句能免掉一整轮 Delphi。用 `cross: false`。
   - 验收轮：逐条判断"已堵住 / 只堵一半 / 没堵住"，**必须引用改后原文**；再问"这轮改动新引入了什么矛盾"，并给"没有就说没有"的出口。用 `cross: false`。
   - 需要某席位带着自己第一轮的立场继续追问细节时，才对它用 `resume: <runId>`。
