# 多模型会议

## 何时用 / 何时不用

**用**：判断题要多视角；我已有判断想被反驳；有 3–5 个互斥方案要选一个；稿件改了几轮需要"验收"（有没有引入新矛盾）；需要机制层面的挑错。

**不用**：事实查询（用 `web_search`）、代码实现（直接做）、只有一个合理答案的问题、需要真实读者数据的问题。

## 席位：读配置，不要写死

席位表在 pi 配置目录下的 `ai-meeting.json`，通常是 `~/.pi/agent/ai-meeting.json`（准确路径看 `/ai-meeting:config` 的输出）。

- **文件不存在**，或用户想换席位的模型 → **让用户运行 `/ai-meeting:config`**。它交互式地逐席选"供应商 → 模型 → 思考档位"，只列出真实可用、且该模型支持的档位；`/ai-meeting:config raw` 则直接用编辑器改 JSON。
- **绝对不要自己编模型 id**：不在注册表里的模型会让那个席位 0 秒硬失败。要列可选模型用 `pi --list-models`。
- 不要替用户改这个文件；它是用户自己的实测配置。

```json
{
  "version": 1,
  "seats": [
    { "provider": "anthropic", "model": "claude-opus-4", "thinking": "high", "name": "opus", "note": "结构最清，保守" }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `provider` / `model` | 必须是注册表里真实存在的组合；传给子会话时拼成 `provider/model:thinking` |
| `thinking` | 必须是该模型 `thinkingLevelMap` 里非 null 的档（交互式配置只会列合法档位） |
| `name` | 席位简称：用作子会话 key 和"谁改了什么主意"的标签，**必须唯一** |
| `note` | 只给人看的实测特点，不影响开会 |

- **3–5 席**合适。2 席只能互相对拍，6 席以上成本线性涨而边际收益掉。
- **席位之间必须真的是不同模型**：同一个模型挂在两个供应商名下只是重复，不算独立视角。
- 供应商的认证、可用模型清单都是用户本机的事，不要假设别的机器上有同样的模型。

### 怎么摸清各席位的脾气

开会前你不知道谁保守、谁爱改判。方法：拿一个**你自己已经有答案**的判断题开一次会（`cross: false` 就够），看谁敢推翻你、谁只是复述。把观察写进对应席位的 `note`。经验上值钱的特征有：敢不敢改判、会不会抓机制漏洞、静默思考多久、是否忽略格式约束。

## 三条硬规矩（违反必出事）

1. **换过模型后，先让用户在 pi 里按一次 `/model` 重载注册表**。否则该席位硬失败：`Unknown subagent model '...' in the active Pi model registry`。（硬失败比静默打到旧模型上强。）
2. **开会就是一次 `subagent` 调用，必须给 `timeoutMs`**，`runs.all` 会被最慢的席位绑架；单席位失败由脚本兜住，不许带崩整场。
3. **不许下"精确字数"约束**——实测有模型会起 `bash` + `python` 数字数，拖慢整场。写成"控制在 N 字左右，**不必精确，不要为此运行命令**"。

## 流程

0. **先确认依赖在不在（每次开会前一次）**：工具列表里必须有 `subagent`。没有就**停下来**告诉用户：

   > 开会需要 `pi-subagents`（不是 pi 自带的），先装：`pi install npm:pi-subagents`，装完重开会话

   它的 `oracle` agent 也是开会用的默认席位载体（不确定就用 `subagent({action:"list", capabilities:true})` 确认）。**不要用别的工具假装开会**，也不要换个 agent 硬跑。

1. **读配置 + 写问题单**（写法与六类会议模板见 `references/question-design.md`）：逼具体、给**机制契约**、允许它们反驳我、允许它们自己写一版。
2. **开会**——脚本是现成的，直接当脚本文件调用，不要复制代码进回复：

```js
subagent({
  // 把 <skill 目录> 换成你系统提示里 ai-meeting skill 的真实目录（就是 SKILL.md 所在的上一级），
  // 不要把这个占位符原样照抄，也不要把 references/meeting.js 的代码复制进回复
  workflow: "<skill 目录>/references/meeting.js",
  async: true,
  timeoutMs: 1800000,
  args: {
    seats: [ /* 原样粘贴 ai-meeting.json 里的 seats 数组，别改字段名 */ ],
    brief: "问题单全文（自包含）",
    cross: true,
    tag: "设定-0725"
  }
})
```

- `cross: true`：第一轮并行独立表态（`context: fresh`，互相隔离）**＋** 第二轮匿名交叉质询，一次跑完。审稿、机制挑错、方案选型用 `true`。
- `cross: false`：只跑第一轮，约省一半时间。只想快速取值、或问题本身没有分歧余地时用。
  门控靠这里：两种都在**启动前**决定；`cross: true` 时若第一轮高度一致，第二轮直接当没发生、不当依据即可。**不要为了补质询轮重跑第一轮。**
- `brief` 要自包含：席位是 fresh 上下文，没有你的上一轮。长材料**写绝对路径让它们自己 `read`**（`args` 上限 16 KiB）。
- 返回值里每个席位都带 `runId`（第一轮、第二轮各一个），后续轮次用它 `resume`——不要重跑第一轮。
- `seat` 是配置里的 `name`（给人看的）；两席同名时脚本会把 key 自动去重成 `probe-b` / `probe-b-2`，**票型里要用 `key` 区分它们**，别写成两个一样的名字。
- `async: true` 会先返回执据，完成才有返回值：**等到通知/返回值再汇总**，不要凭开会过程中的局部输出下结论。

3. **会后必做四件事**（顺序固定，缺一件算没做完）：

   **① 拖时间甄别** —— 见下面那节。有异常先单独报给用户，再给结论。

   **② 票型图** —— 先说清这次是**统一**还是**未统一**；未统一就把各方向列成 A/B/C，每个方向写「票数 ＋ 席名 ＋ 一句话主张」。格式：

   ```markdown
   ## 票型：未统一（4 席 2/1/1）

   **A「保留原机制，只补边界条款」2 票 —— sol、grok**
   一句话：不推翻现有体系，把代价写成显式条件，冲突处加例外条款。
   代价：机制复杂度继续上升。

   **B「换成成本更低的新机制」1 票 —— astra**
   一句话：……

   **C「先不动，等更多数据」1 票 —— ds**
   一句话：……

   分歧的实质：A 与 B 争的是改动幅度；C 不是第三个方向，是对信息量的保留意见。
   ```

   - 聚类按**主张的可执行差异**（改哪、改成什么、代价），**不按措辞**；同一方向必须先能一句话概括。
   - 一票的方向也要列，别只报多数。方向用 A/B/C 标，票数用**席位数量**。
   - **四家四说（各 1 票）不要硬凑方向**：直接说"问题本身没收敛"，并建议重写问题单（通常是问法太宽）。
   - 统一时写「票型：统一（N/N）」，但**仍要单列唯一反对者或少数意见**——那往往是最有信息量的部分。
   - 脚本返回值里每席都带 `stance`（从答案末尾的 `【结论】` 行抓的）**并已优先取第二轮**（第二轮出现改判时，只用第一轮就是报旧票型——实测发生过）；`stanceRound` 标明它来自哪一轮。抓到 null 就回读原文自己归纳。

   **③ 分三类**（做法见 `references/question-design.md`）：**真洞 / 我已知的取舍 / 空话**；**逐条回读原文验证**，不当传声筒；单列"**谁改了什么主意**"。

   **④ 下一步菜单** —— 给用户 4–5 个带代价的选项，**不替用户选**：

   ```markdown
   ## 下一步（选一个，或给我一个新方向）

   1. 采用 A（或某个方向）—— 我不再开会，直接按它出具体改法
   2. 四席二轮会：把 A/B/C 匿名列成选项重新表态（不告诉谁提的），看票型是否移动 —— cross: true
   3. 三席两轮会（交叉验证）：移出最边缘的一席，让 A/B 对撞，目标是收敛出统一方向
      —— 只传 seats 子集即可，不用改配置；cross: true
   4. 只深挖某一方向：指定 A/B/C，我把它写成待验证假设，让各席找它的反例与失效条件 —— cross: true
   5. 你给一个新方向：写进问题单开二轮会
   ```

   - 选项 2/3 要**带上本轮的耗时结论**（例："若 grok 又垫底，建议先降到 high 再开"）。
   - **最多两轮**（一轮表态 + 一轮收敛）。第二轮仍分裂就不再开会，把分歧与各自代价摆给用户拍板——**不要用开会去"等统一"**。
   - 统一时菜单收窄成：采用 / 深挖反例 / 用户给新方向（省掉收敛轮）。
   - 投票轮的固定格式（一行票 + 一行理由 + "少数时我接受谁"）见 `references/question-design.md`，那一句能免掉一整轮 Delphi。

4. **验收会**（用户按结论改完之后另开一场，`cross: false`）：逐条判断"已堵住 / 只堵一半 / 没堵住"，**必须引用改后原文**；再问"这轮改动新引入了什么矛盾"，并给"没有就说没有"的出口。

## 拖时间甄别（每场会开完都要做）

一场会里只要有一个席位持续慢 2–3 倍，整个会就被它拖住。反过来，一个席位如果快得反常，很可能是**没真读材料就答了**。两种都要发现并告诉用户，但**先分清是哪一种，不要误伤只是快的模型**。

**耗时从哪来（结构化，别解析文本）**

每个席位返回的 `asyncDir` 下都有 `status.json`，单席耗时在 `steps[0].durationMs`（毫秒），同一文件里还有 `steps[0].model`（含档位）、`turnCount`、`totalTokens`。把各席 `asyncDir` 换成自己的路径跑：

```bash
node -e "const fs=require('fs'),args=process.argv.slice(1),i=args.indexOf('--');const pats=args.slice(0,i<0?0:i),dirs=args.slice(i+1);for(const p of dirs){const st=JSON.parse(fs.readFileSync(p+'/status.json','utf8')),s=(st.steps||[{}])[0];const ms=s.durationMs||(st.endedAt-st.startedAt);const calls=[];for(const line of fs.readFileSync(p+'/events.jsonl','utf8').split('\n')){if(!line)continue;let e;try{e=JSON.parse(line)}catch{continue}if(e.type==='tool_execution_start')calls.push(e.toolName+' '+JSON.stringify(e.args||{}))}const hits=pats.filter(pt=>calls.some(c=>c.includes(pt)));const names={};for(const c of calls){const n=c.split(' ')[0];names[n]=(names[n]||0)+1}console.log((st.workflowKey||'').padEnd(8),Math.round(ms/1000)+'s','tools='+st.toolCount,'turns='+st.turnCount,'inTok='+(st.totalTokens||{}).input,'| 工具:',JSON.stringify(names),'| 碰过材料',hits.length+'/'+pats.length)}" "<关键材料名或路径片段 1>" "<片段 2>" -- <asyncDir...>
```

- 这是 **pi-subagents 的内部布局**，不是公开契约（另一条路——读返回值里的耗时——实测走不通：`results[0]` 里连时间字段都没有，`progressSummary` 已被投影掉）。**读不到就直说"耗时未知"**，不要拿别的数字充数。
- 优先用 `node`（pi 的宿主运行时）；没有就用 python 或任何能读 JSON 的方式，都没有就报未知。**不要为此安装任何东西**。
- `--` 后面是各席 asyncDir，前面是本次材料的关键字（文件名片段就够）。

**判据一：谁在拖时间（≥3 席才判；2 席分不出谁是异类）**

用**中位数**比，不用绝对秒数——子会话有秒级固定开销，且**同一席位跨场能拖 6 倍**（实测同一句"只回复 ok"：deepseek-flash 两场 33.9 秒 / 5.2 秒）。

1. **慢席位**：某席 ≥ 中位数 × **2.0**，且比中位数多 60 秒以上。两个条件都要（单场光看比值就是噪声）。
   阈值原本是 2.5×，实测漏报过一次：grok 436.7 秒 / 中位数 177.5 秒 = 2.46×，它一个席位比其他三席之和还多，却没报警。
2. **先看档位**：`steps[0].model` 尾部就是档位（`provider/model:xhigh`）。该席档位明显高于其他席（xhigh/max vs medium/high）时，**先建议降一档重开一场**，别急着踢人。（实测：grok 是唯一 xhigh，436.7 秒。）
3. **再看调用构成**：实测同样覆盖全部材料，一个席位用 **4 次批量 bash**（65 秒），另一个用 **79 次细碎 grep/read**（437 秒）——**慢的原因常常是调用碎，不是干得多**。看到慢席位 `tools` 数极高时，把它说成"调用碎 + 往返开销"，别污蔑它效率低；降档或换模型才是对症的。

**判据二：有没有真读材料（只看直接证据）**

**唯一算数的证据是它到底碰没碰过材料**：命令里的"碰过材料 N/M"就是从工具调用参数里数出来的（不管它用 `read` 还是用 `bash`+`nl` 把文件打出来，都算碰上）。

- **N/M 满 → 不是摸鱼**，无论它多快。实测反例：astra 65.4 秒（0.37× 中位数）、输入 token 只有同族席位的 91%，但它 4 次批量 bash 覆盖了全部材料，还自己写了脚本复现出一个真 bug——凭"快 + 短 + token 少"判它摸鱼就是误伤。
- **N/M 为 0–1 且 tools 极少（≤2）** → 才说"疑似没读材料"，并把命中情况直接摆给用户（"它一次都没打开过 X"是事实，不是推断）。
- **不要拿 `turns`／`inTok`／`chars` 当判据**：一个 turn 里可以并发多个工具调用，所以 turns 会严重少算工作量（实测 astra 5 turns / 4 tools 就翻完了整个仓库，grok 47 turns 做的是同一件事）；token 与字符数则受模型风格影响。这三个数字只能当上下文。

**怎么告诉用户**

在结论前面单独一段，写三件事：① 每席耗时与中位数（秒）；② 你的判断——**档位/调用风格问题** / **疑似没读材料（附命中数）** / **只是快**；③ 建议三选一：**降档重开** / **用 `/ai-meeting:config` 把那一席减掉改成 N-1 席** / **换一个模型**。

另外三条纪律：

- **不要自己静默改配置或替用户减席位**。改配置是用户的事，也改变"独立视角"的构成——给完建议等用户定。
- **单场异常先观察**：同一席连续两场都垫底再建议动手（单场抖动很常见）。
- `totalCost.costUsd` 常见为 0：那是供应商没回传价格，**不等于免费**。
