# 实战坑与修法

## 环境与启动

1. **模型不在注册表里就 0 秒硬失败**。改了 `models.json` 或 `ai-meeting.json` 里的模型后，必须让用户在 pi 里按一次 `/model` 重载注册表，否则：`Unknown subagent model '...' in the active Pi model registry`。
   （硬失败比静默打到别的模型上强。）给别人的机器写死某个模型 id 一定出事——所以席位一律走配置。
2. **席位的档位必须落在模型自己的 `thinkingLevelMap` 里**（`null` 的档不支持）。例如某些供应商的模型只有 low/high/max（给 medium 直接失败）、有的没有 off。`/ai-meeting:config` 的交互式选择只会列合法档位，手写 JSON 时别猜。
3. **配置默认席位要按模型 id 去重，不能只按供应商**。同一个模型常挂在多个供应商别名下（网关／区域／代理商），只按供应商轮转会把四席选成同一个模型的四次重复。默认生成逻辑也优先用户当前会话所在的供应商。

## 速度与稳定性

4. **绝不下"精确字数"约束**。实测有模型会起 `bash` + `python -c` 统计中文字符数（还改了两版），拖慢整场。写成"控制在 N 字左右，不必精确，不要为此运行命令"。
5. **`runs.all` 会被最慢席位绑架**：一个卡住的席位能让整场空等（默认 30 分钟上限）。每次 `subagent` 调用都要给 `timeoutMs`。
6. **高思考档的静默期很长**：xhigh 档的模型常常 60–140 秒零输出、零 token 记录，然后一次性吐完。**别急着判它卡死**（误杀过还在正常思考的席位）。区分方法看 `lastActivityAt` 与 `turnCount`。
7. **第二轮写成顺序 `for` 就等于慢 N 倍**。第二轮彼此无依赖，必须在一次 `runs.all` 里发出。

## 耗时与"摸鱼"判断

8. **单席位耗时不在 run 结果里**：把 `results[0]` 的全部键打出来只有 `index/agent/sessionName/task/exitCode/usage/finalOutput/outputState/sessionFile/model/requestedModel/acceptance/artifactPaths/transcriptPath`——没有 `durationMs`，也没有 `progressSummary`（类型里确实有 `ProgressSummary.durationMs`，但跨到脚本时被投影掉了）。**所以在脚本里加耗时字段这条路是死的**，别听"改读 `progressSummary`"就改。
   真出处：每个席位 `asyncDir` 的 `status.json` 里 `steps[0].durationMs`（还有 `model`、`turnCount`、`totalTokens`）——但那是 pi-subagents 的**内部布局**，不是公开契约，读不到就要报"耗时未知"。
   一句教训：我第一次找时间字段时用 `Object.keys` �么结果筛 `/dur|time|ms/`，漏了嵌套键就下了"没有时间字段"的结论；正确做法是**把全部键打出来看**。
9. **不能用绝对秒数判快慢**：子会话有秒级固定开销——实测一个只要求"回复 ok"的子会话也要 33.9 秒。所以"它 10 秒就答完了"这种判断在实测里不成立，快慢一律跟**本场中位数**比。
   更麻烦的是**同一席位跨场能拖 6 倍**：同一句"只回复 ok"，deepseek-flash 两场分别 33.9 秒和 5.2 秒。所以单场耗时只是**信号**，判据必须带绝对差值（多/少 60 秒以上），且**连续两场**都异常才建议用户动手。
   **阈值实测校准过一次**：原本写 ≥2.5×，一场真实审稿会里 grok 436.7 秒 / 中位数 177.5 秒 = 2.46×——它一个席位比其他三席之和还多，却刚好卡在阈值下没报警。改成 **2.0×**（仍带 +60 秒条件）。
10. **慢的主因常常是档位不是模型**。同一场实测：grok 是唯一 xhigh，436.7 秒；其余 medium/medium/high，65.4 / 95.8 / 259.2 秒。看到某席垫底先看它的档位，档位明显高于别人就先建议降档重开，再谈踢人。
11. **判"摸鱼"只能看直接证据：它到底碰没碰过材料**（从工具调用参数里数材料命中数）。**任何代理指标都不算——我在这一个判据上连错两次**：
    - 先用 `inputTokens` + `chars`：差点误伤 astra（65.4 秒 / 0.37× 中位数 / token 只有同族席位的 91%，但它独立报出两个真 bug）。
    - 换成 `turns`：**用户一眼看穿这是同类错误**——一个 turn 里可以并发多个工具调用，所以 turns 会严重少算工作量。实测 astra 是 **5 turns / 4 tools** 翻完了整个仓库，grok 是 **47 turns / 79 tools** 干了同一件事；看 turns 会把最能干的席位误判成摸鱼。
    正确做法（命令在 SKILL.md）：从 `events.jsonl` 的 `tool_execution_start` 里抽出每个席位的工具调用，看参数里有没有本次材料的关键字——**不管它是用 `read` 还是用 `bash` + `nl` 把文件打出来，都算碰上**。实测那场四席全是 4/4，没有人摸鱼。
12. **`tools` 多不等于干得多，往往只等于调用碎**。同一场实测：astra 4 次批量 bash（一次就 `nl` 六个文件）→ 65 秒；sol 4 次 → 96 秒；grok 79 次细碎 grep/read → 437 秒；ds 80 次 bash → 259 秒。**慢的主因是"调用次数 × 单次往返开销"**，不是工作量。跟用户报时要写成"调用碎 + 高思考档"，不要写成"它效率低"——建议也是降档/换模型，而不是叫它少干活。

## 脚本本身的坑（都实测过）

13. **`resume` 的子会话会沿用原会话的输出路径**：同一轮里"第一轮子会话"和"它的 r2 续跑"会抢同一个文件，直接失败（`resolve output to the same path`）。给 resume 的 item 显式换一个 `output` 路径，或者干脆 `output: false`。
14. **`runs.run` 写在 `.catch(() => ...)` 里会被判违规**：workflow 结束时报 `completed with unawaited runs.run launch(es)`，整场标 failed。兜底不能写成 promise 链里的嵌套启动，要写成**两段式**：先 `await runs.all(...)` 收下所有结果，再对失败的那批 `await runs.all(...)` 重跑。
15. **给子会话设了 `output` 会污染返回文本**：返回值尾巴上会多一句 `Output saved to: ... (2 B, 1 line)`。第一轮答案要喂给第二轮别家席位时，这句会跟着进去。要干净就 `output: false`；留档由汇总时自己写文件。
16. **脚本里的 `outputReference` 是字符串路径，不是对象**。`results[0].savedOutputPath`、`outputArtifactPath`、`artifactPaths` 也都在。踩过一次：按 `outputReference.path` 读，读出 undefined，误判成"脚本拿不到落盘路径"。
17. **`resume` 不是必然成功**，所以要有降级分支——但降级必须走第 14 条的两段式写法。**单席位失败绝不能带崩整场**：失败席位标成缺席，其余照常汇总。

## 主持人的自身错误

18. **给了材料就别再塞我自己的分析**，除非明确要它们反驳我。塞了会被锚定；不塞才能拿到独立判断（多次出现"它们独立指出的问题"比"我塞进去的"更狠）。
19. **匿名**：第二轮只喂别家答案、不标是谁；投票选项也不标谁提的。否则会变成"是我提的我就坚持"。
20. **改动必须回读文件核对，不能凭记忆**。误记自己改过某段设定，导致整批替换锚点失败、白跑一轮。做法：改完用一次校验命令回读关键字段。

## 依赖（pi-subagents）的坑

21. **`pi-subagents` 不是 pi 自带的，也不会跟着本包自动装上**。实测：pi 自己的 dependencies 里没有它（只有 `@earendil-works/*`、chord、mcp、tui 那些），pi 的 docs 里一次都没提 subagent；它是独立的 `npm:pi-subagents`。所以 README 和 SKILL.md 流程第 0 步都要提醒，不然别人（或换了机器）第一次开会就是"没有 subagent 工具"。
22. **不要把 `pi-subagents` 写进本包的 `dependencies`**。pi 确实会给 npm/git 包装依赖，但另一个 Pi 包当依赖必须连同 tarball 发布、并手写 `node_modules` 资源路径；而用户自己也装了一份时，会出现两份 `subagent` 工具与两套 agent 注册表（官方 docs 明确警告重复的 classes/registries）。正确做法：当作前置条件 + 第 0 步检测。
23. **扩展的 `readonly tools` 只在 `ExtensionToolContext`（执行工具时）上才有**。命令处理器（`ExtensionCommandContext`）拿不到工具列表，所以"缺依赖就在 `/ai-meeting:config` 里弹提醒"做不到——检测只能由主持人看自己的工具列表（那也是最准的检测）。

## 装成 pi 包之后的坑

24. **不要再往 `~/.pi/agent/skills/` 放一份同名副本**。同名 skill 冲突时 pi"保留先发现的 + 只打个警告"，本地那份会静默盖掉包里的版本，改包不生效。改动走仓库 → `pi update <source>`；会话中改完 SKILL.md 用 `/reload`。
25. **`pi remove` 不会删配置文件**。实测：包目录（含 `git/github.com/<user>/pi-ai-meeting` 和空掉的父目录）、settings 条目都会被清掉，但 `~/.pi/agent/ai-meeting.json` **留在原地**。而且扩展 API 没有卸载钩子（38 个事件名里没有任何 uninstall/remove 一类），包在被移除的那一刻没有代码可执行，清不掉自己的文件。所以移除前先自己删那个文件；这类配置也只能放在包外（放包内会被 `pi update` 的 reconcile 覆盖）。
26. **扩展命令名里的 `:` 不特殊**（`/ai-meeting:config` 就是普通命令名），但如果另一个包注册了同名命令，pi 会自动加 `:2` 后缀，用户看到的就不一样了。

## 汇总与收敛的坑

27. **回答里可能混进 harness 报告块**。实测 `gpt-6.1-sol` 在一次普通表态里，回答开头自己塞了一整块 ```acceptance-report 的 JSON（`oracle` 的 agent 定义里并没有 acceptance，是供应商网关侧的行为，我控制不了）。后果：污染第二轮互喂的答案、把 `chars` 从 139 灌到 456、干扰票型聚类。两道防线：`meeting.js` 从答案开头剥掉这种块（`cleanText`，只认已知标签，不会误删正常的代码块）；问题单里明说不要输出这种块。
28. **不要把"方向"按措辞分**。两家都说"加强约束"，一家要改机制、一家只加例外条款，那是**两个方向**。聚类标准是**可执行差异**（改哪、改成什么、代价），不是词汇重合；同一方向必须先能一句话概括。
29. **四家四说不要硬凑方向**。各 1 票时正确做法是宣布"问题本身没收敛"并建议重写问题单（通常是问法太宽），而不是把两家硬并成一个方向来好看。
30. **开会不是为了"开到统一"**。上限两轮（表态 + 收敛）；第二轮仍分裂就停，把分歧与各自代价摆给用户拍板。无限开会的成本是线性涨的，而分裂往往是"信息不够/口味不同"，再开也收不了。
31. **菜单不能替用户选**。给出选项、代价和耗时实情，等用户定；用户说"你定"才自己选并说明理由。实测最危险的做法是拿 2:1 的票数去压作者直觉（投票会把方案推向"信息更全"，而创作类的 KPI 不是信息完整）。

## 一场审稿会审出来的坑（v1.2.0 → v1.3.0）

拿这个包自己开了一场四席审稿会（四席审自己的代码），下面是它们找出、我逐条核实后确认的真 bug：

32. **坏配置被当成"没配置"→ 静默覆盖（最严重）**。`readConfig` 用一个 `catch` 把"文件不存在"和"JSON 坏了"压成同一个 `undefined`，handler 紧接着生成默认四席并 `writeConfig`，提示还写着"已按当前可用模型生成默认配置"（读起来像成功）。用户手写 JSON 打错一个逗号，下次只想看一眼配置就丢掉全部 `name`/`note`。修法：读文件分**三态**（missing / invalid / ok），只有 missing 才写默认；invalid 就报错停下、一个字不写。
33. **校验函数会被用户的合法 JSON 弄崩**。`validate` 直接摸 `config.seats.length`。把真函数抠出来实测：`null`、`{}`、`{"seats":[null]}`、`{"seats":"x"}` 四种**合法 JSON** 全抛 TypeError（raw 编辑器路径直接把用户输入喂给它）。修法：先查结构再查内容，任何输入都不许抛。
34. **`name` 会被当 workflow key，字符集和唯一性不查就炸场**。key 的硬约束是 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` 且同批不能重复：中文名/空格 → 整场**运行时**报 `invalid key`（报错里不会出现 `name`）；同名同参 → 被静默复用成**一份答案**（两席变一席）。两层修：扩展的 `validate` 拦非法名与重名；脚本再把 key 自动安全化去重（`seat1` / `probe-b` / `probe-b-2`），重名时票型用 `key` 区分。
35. **兜底分支必须把原题单一起给新会话**。`resume` 失败降级成 fresh 时，只传了"互评包 + 它自己第一轮的答案"，**没有 `brief`**——新会话会对着没有问题的材料作答，不报错、不缺席，主持人只看到答非所问。这是全场最隐蔽的一条，三家独立命中。
36. **第二轮的格式要求必须重写一遍**。第一轮要求了 `【结论】` 不代表第二轮会给：`packetFor` 只写了三点编号，实测有席位顺势写成"修订结论"，于是 `stance` 抽到 `null`（下一场就复现了）。
37. **票型必须读第二轮立场**。`perSeat.stance` 原本只来自第一轮，而第二轮常出现改判（那场审稿会：三家在第二轮改口不拆轮次）——用第一轮汇总就会报一份过时的票型。修法：`perSeat.stance` 优先取第二轮，并用 `stanceRound` 标明来源。
38. **同一命令名被两个来源注册，原名会直接失效**。实测：包里已装了带 `extensions/ai-meeting.ts` 的版本，再用 `pi -e <同一文件>` 加载一遍，`/ai-meeting:config` 就不接管了——文字被当成**普通提示词**发给模型（还白花一次调用）。pi 的处置是给重名命令加 `:1`/`:2` 后缀。测试扩展时用 `PI_CODING_AGENT_DIR=<临时目录>` 隔离（把 `auth.json`/`models.json` 拷过去、`settings.json` 里 `packages` 置空），不要靠 `-e` 叠在已安装的包上。
39. **`ctx.ui.notify` 在 print/json 模式下是空操作**。无 UI 时错误“没有任何输出”，看起来像命令根本没跑。要自己分流：有 UI 就 `notify`，否则 `console.log`。

39. **“降档”不一定治慢**。实测：某席 xhigh 时 437 秒（重任务），降到 high 后 **423 秒**（任务还小得多），仍是最慢的那个（另两席 40s / 57s）。它 3 次请求就吐了 49,840 输出 token。所以降档只在“慢是思考深度导致的”时有效，要先测再下结论（而它的钱很便宜：$0.162）。
40. **不要把自己没核实的数据喂给席位**。一次会议里我给席位的简报写了一个窗口开太宽的“主持人花了 $39”，结果 **3/3 席位据此把“主会话/主持人轮询”排到第一优先级**——而实测那个真实窗口里主持人只花了 $0.84、只发了 2 次请求（`async` 会议期间根本不轮询）。错的前提会产出一致但错误的共识，比分歧更危险。给席位的数据必须先自己核过。

## 附：两个反直觉的观察

**投票会把方案推向"信息更全"，但创作类的 KPI 不是信息完整**（是点击、是追读、是好看）。所以：

- 投票适合**判断题**（要不要改、选哪个方案、哪条规则更自洽）；
- 投票**不适合**润色题（文案、简介、诗）——这类要让作者直觉优先，会可以开，但结论只作参考。
- 一句话：**会用来解决分歧，不用来追求完备。**

**交叉质询只在真有分歧时值钱**。四家措辞不同、结论一致时，第二轮基本是互相复述（实测两席互相回答"无分歧／没被说服"）——这种情况直接汇总，别把第二轮当依据。
