# 实战坑与修法

## 环境与启动

1. **模型不在注册表里就 0 秒硬失败**。改了 `models.json` 或 `ai-meeting.json` 里的模型后，必须让用户在 pi 里按一次 `/model` 重载注册表，否则：`Unknown subagent model '...' in the active Pi model registry`。
   （硬失败比静默打到别的模型上强。）给别人的机器写死某个模型 id 一定出事——所以席位一律走配置。
2. **席位的档位必须落在模型自己的 `thinkingLevelMap` 里**（`null` 的档不支持）。例如某些供应商的模型只有 low/high/max（给 medium 直接失败）、有的没有 off。`/ai-meeting:config` 的交互式选择只会列合法档位，手写 JSON 时别猜。
3. **配置默认席位要按模型 id 去重，不能只按供应商**。同一个模型常挂在多个供应商别名下（网关／区域／代理商），只按供应商轮转会把四席选成同一个模型的四次重复。默认生成逻辑也优先用户当前会话所在的供应商。

## 速度与稳定性

4. **绝不下"精确字数"约束**。实测有模型会起 `bash` + `python -c` 统计中文字符数（还改了两版），拖慢整场。写成"控制在 N 字左右，不必精确，不要为此运行命令"。
5. **`runs.all` 会被最慢席位绑架**：一个卡住的席位能让整场空等（默认 30 分钟上限）。每次 `subagent` 调用都要给 `timeoutMs`。
6. **高思考档的静默期很长**：xhigh 档的模型常常 60–140 秒零输出、零 token 记录，然后一次性吐完。**别急着判它卡死**（误杀过还在正常思考的席位）。区分方法看 `lastActivityAt` 与 `turnCount`。
7. **第二轮写成顺序 `for` 就等于慢 N 倍**。第二轮彼此无依赖，必须在一次 `runs.all` 里发出。

## 脚本本身的坑（都实测过）

8. **`resume` 的子会话会沿用原会话的输出路径**：同一轮里"第一轮子会话"和"它的 r2 续跑"会抢同一个文件，直接失败（`resolve output to the same path`）。给 resume 的 item 显式换一个 `output` 路径，或者干脆 `output: false`。
9. **`runs.run` 写在 `.catch(() => ...)` 里会被判违规**：workflow 结束时报 `completed with unawaited runs.run launch(es)`，整场标 failed。兜底不能写成 promise 链里的嵌套启动，要写成**两段式**：先 `await runs.all(...)` 收下所有结果，再对失败的那批 `await runs.all(...)` 重跑。
10. **脚本里拿不到 `outputReference`**：子会话结果是纯 JSON 数据，host 元数据（含真实落盘路径）在边界处被丢掉，读到的永远是 null。别在脚本里做路径编排。
11. **给子会话设了 `output` 会污染返回文本**：返回值尾巴上会多一句 `Output saved to: ... (...)`。第一轮答案要喂给第二轮别家席位时，这句会跟着进去。要干净就 `output: false`；留档由汇总时自己写文件。
12. **`resume` 不是必然成功**，所以要有降级分支——但降级必须走第 9 条的两段式写法。**单席位失败绝不能带崩整场**：失败席位标成缺席，其余照常汇总。

## 主持人的自身错误

13. **给了材料就别再塞我自己的分析**，除非明确要它们反驳我。塞了会被锚定；不塞才能拿到独立判断（多次出现"它们独立指出的问题"比"我塞进去的"更狠）。
14. **匿名**：第二轮只喂别家答案、不标是谁；投票选项也不标谁提的。否则会变成"是我提的我就坚持"。
15. **改动必须回读文件核对，不能凭记忆**。误记自己改过某段设定，导致整批替换锚点失败、白跑一轮。做法：改完用一次校验命令回读关键字段。

## 装成 pi 包之后的坑

16. **不要再往 `~/.pi/agent/skills/` 放一份同名副本**。同名 skill 冲突时 pi"保留先发现的 + 只打个警告"，本地那份会静默盖掉包里的版本，改包不生效。改动走仓库 → `pi update <source>`；会话中改完 SKILL.md 用 `/reload`。
17. **扩展命令名里的 `:` 不特殊**（`/ai-meeting:config` 就是普通命令名），但如果另一个包注册了同名命令，pi 会自动加 `:2` 后缀，用户看到的就不一样了。

## 附：一个反直觉的观察

**投票会把方案推向"信息更全"，但创作类的 KPI 不是信息完整**（是点击、是追读、是好看）。所以：

- 投票适合**判断题**（要不要改、选哪个方案、哪条规则更自洽）；
- 投票**不适合**润色题（文案、简介、诗）——这类要让作者直觉优先，会可以开，但结论只作参考。
- 一句话：**会用来解决分歧，不用来追求完备。**

另一条同类的：**交叉质询只在真有分歧时值钱**。四家措辞不同、结论一致时，第二轮基本是互相复述（实测两席互相回答"无分歧／没被说服"）——这种情况直接汇总，别把第二轮当依据。
