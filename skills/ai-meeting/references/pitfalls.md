# 实战坑与修法

## 环境与启动

1. **模型不在注册表里就 0 秒硬失败**。改了 `models.json` 或 `ai-meeting.json` 里的模型后，必须让用户在 pi 里按一次 `/model` 重载注册表，否则：`Unknown subagent model '...' in the active Pi model registry`。
   （硬失败比静默打到别的模型上强。）给别人的机器写死某个模型 id 一定出事——所以席位一律走配置。
2. **席位的档位必须落在模型自己的 `thinkingLevelMap` 里**（`null` 的档不支持）。例如某些供应商的模型只有 low/high/max（给 medium 直接失败）、有的没有 off。`/ai-meeting:config` 的交互式选择只会列合法档位，手写 JSON 时别猜。
3. **配置默认席位要按模型 id 去重，不能只按供应商**。同一个模型常挂在多个供应商别名下（网关／区域／代理商），只按供应商轮转会把四席选成同一个模型的四次重复。默认生成逻辑也优先用户当前会话所在的供应商。

## 速度与稳定性

4. **绝不下"精确字数"约束**。实测有模型会起 `bash` + `python -c` 统计中文字符数（还改了两版），拖慢整场。写成"控制在 N 字左右，不必精确，不要为此运行命令"。
5. **`runs.all` 会被最慢席位绑架**：一个卡住的席位能让整场空等（默认 30 分钟上限）。每次 `subagent` 调用都要给 `timeoutMs`。
6. **高思考档的静默期很长**：xhigh 档的模型常常 60–140 秒零输出、零 token 记录，然后一次性吐完。**别急着判它卡死**（误杀过还在正常思考的席位）。区分方法看 `lastActivityAt` 与 `turnCount`。
7. **第二轮写成顺序 `for` 就等于慢 N 倍**。第二轮彼此无依赖，必须在一次 `runs.all` 里发出。

## 耗时与"摸鱼"判断

8. **单席位耗时不在 run 结果里**：run 结果（含 `results[0]`）里没有任何时间字段（用 `Object.keys` 逐个筛 `/dur|time|elapsed|ms/`，结果为空），所以脚本自己量不到耗时。**但在每个席位 `asyncDir` 的 `status.json` 里有 `steps[0].durationMs`**（还有 `model`、`turnCount`、`totalTokens`、`totalCost`）——结构化数据，按住处读即可。
   **不要用 call trace 判快慢**：那份 `completed (...) in Nms` 文本只是给人看的副本，数字符又脆又不准；实测同一席位那两处数字也不相等（trace 4655ms / status 3276ms）。
9. **不能用绝对秒数判快慢**：子会话有秒级固定开销——实测一个只要求"回复 ok"的子会话也要 33.9 秒。所以"它 10 秒就答完了"这种判断在实测里不成立，快慢一律跟**本场中位数**比。
   更麻烦的是**同一席位跨场能拖 6 倍**：同一句"只回复 ok"，deepseek-flash 两场分别 33.9 秒和 5.2 秒；两席同题同档也能一个 3.8 秒一个 13.9 秒。所以单场耗时只是**信号**，判据必须带绝对差值（多/少 60 秒以上），且**连续两场**都异常才建议用户动手。
10. **慢的主因常常是档位不是模型**。同一个模型在 xhigh 和 medium 下的耗时能差几倍；看到某席垫底先看 `perSeat.model` 尾部的档位，档位明显高于别人就先建议降档重开，再谈踢人。
11. **"快"必须和输入 token／`chars`／`turns` 一起看才叫证据**。`perSeat` 里的 `chars`、`turns`、`inputTokens`、`cost` 来自子会话自己的用量统计：快 + 输入 token 明显少（同 brief 同材料，少几倍就是没读）+ 答案短 = 疑似浑水摸鱼；快但输入 token 与长度都正常 = 只是模型快，**不要误报**。

## 脚本本身的坑（都实测过）

12. **`resume` 的子会话会沿用原会话的输出路径**：同一轮里"第一轮子会话"和"它的 r2 续跑"会抢同一个文件，直接失败（`resolve output to the same path`）。给 resume 的 item 显式换一个 `output` 路径，或者干脆 `output: false`。
13. **`runs.run` 写在 `.catch(() => ...)` 里会被判违规**：workflow 结束时报 `completed with unawaited runs.run launch(es)`，整场标 failed。兜底不能写成 promise 链里的嵌套启动，要写成**两段式**：先 `await runs.all(...)` 收下所有结果，再对失败的那批 `await runs.all(...)` 重跑。
14. **给子会话设了 `output` 会污染返回文本**：返回值尾巴上会多一句 `Output saved to: ... (2 B, 1 line)`。第一轮答案要喂给第二轮别家席位时，这句会跟着进去。要干净就 `output: false`；留档由汇总时自己写文件。
15. **脚本里的 `outputReference` 是字符串路径，不是对象**。`results[0].savedOutputPath`、`outputArtifactPath`、`artifactPaths` 也都在。踩过一次：按 `outputReference.path` 读，读出 undefined，误判成"脚本拿不到落盘路径"。
16. **`resume` 不是必然成功**，所以要有降级分支——但降级必须走第 13 条的两段式写法。**单席位失败绝不能带崩整场**：失败席位标成缺席，其余照常汇总。

## 主持人的自身错误

17. **给了材料就别再塞我自己的分析**，除非明确要它们反驳我。塞了会被锚定；不塞才能拿到独立判断（多次出现"它们独立指出的问题"比"我塞进去的"更狠）。
18. **匿名**：第二轮只喂别家答案、不标是谁；投票选项也不标谁提的。否则会变成"是我提的我就坚持"。
19. **改动必须回读文件核对，不能凭记忆**。误记自己改过某段设定，导致整批替换锚点失败、白跑一轮。做法：改完用一次校验命令回读关键字段。

## 依赖（pi-subagents）的坑

20. **`pi-subagents` 不是 pi 自带的，也不会跟着本包自动装上**。实测：pi 自己的 dependencies 里没有它（只有 `@earendil-works/*`、chord、mcp、tui 那些），pi 的 docs 里一次都没提 subagent；它是独立的 `npm:pi-subagents`。所以 README 和 SKILL.md 流程第 0 步都要提醒，不然别人（或换了机器）第一次开会就是"没有 subagent 工具"。
21. **不要把 `pi-subagents` 写进本包的 `dependencies`**。pi 确实会给 npm/git 包装依赖，但另一个 Pi 包当依赖必须连同 tarball 发布、并手写 `node_modules` 资源路径；而用户自己也装了一份时，会出现两份 `subagent` 工具与两套 agent 注册表（官方 docs 明确警告重复的 classes/registries）。正确做法：当作前置条件 + 第 0 步检测。
22. **扩展的 `readonly tools` 只在 `ExtensionToolContext`（执行工具时）上才有**。命令处理器（`ExtensionCommandContext`）拿不到工具列表，所以"缺依赖就在 `/ai-meeting:config` 里弹提醒"做不到——检测只能由主持人看自己的工具列表（那也是最准的检测）。

## 装成 pi 包之后的坑

23. **不要再往 `~/.pi/agent/skills/` 放一份同名副本**。同名 skill 冲突时 pi"保留先发现的 + 只打个警告"，本地那份会静默盖掉包里的版本，改包不生效。改动走仓库 → `pi update <source>`；会话中改完 SKILL.md 用 `/reload`。
24. **`pi remove` 不会删配置文件**。实测：包目录（含 `git/github.com/<user>/pi-ai-meeting` 和空掉的父目录）、settings 条目都会被清掉，但 `~/.pi/agent/ai-meeting.json` **留在原地**。而且扩展 API 没有卸载钩子（38 个事件名里没有任何 uninstall/remove 一类），包在被移除的那一刻没有代码可执行，清不掉自己的文件。所以移除前先自己删那个文件；这类配置也只能放在包外（放包内会被 `pi update` 的 reconcile 覆盖）。
25. **扩展命令名里的 `:` 不特殊**（`/ai-meeting:config` 就是普通命令名），但如果另一个包注册了同名命令，pi 会自动加 `:2` 后缀，用户看到的就不一样了。

## 汇总与收敛的坑

26. **回答里可能混进 harness 报告块**。实测 `gpt-6.1-sol` 在一次普通表态里，回答开头自己塞了一整块 ```acceptance-report 的 JSON（`oracle` 的 agent 定义里并没有 acceptance，是供应商网关侧的行为，我控制不了）。后果：污染第二轮互喂的答案、把 `chars` 从 139 灌到 456、干扰票型聚类。两道防线：`meeting.js` 从答案开头剥掉这种块（`cleanText`，只认已知标签，不会误删正常的代码块）；问题单里明说不要输出这种块。
27. **不要把"方向"按措辞分**。两家都说"加强约束"，一家要改机制、一家只加例外条款，那是**两个方向**。聚类标准是**可执行差异**（改哪、改成什么、代价），不是词汇重合；同一方向必须先能一句话概括。
28. **四家四说不要硬凑方向**。各 1 票时正确做法是宣布"问题本身没收敛"并建议重写问题单（通常是问法太宽），而不是把两家硬并成一个方向来好看。
29. **开会不是为了"开到统一"**。上限两轮（表态 + 收敛）；第二轮仍分裂就停，把分歧与各自代价摆给用户拍板。无限开会的成本是线性涨的，而分裂往往是"信息不够/口味不同"，再开也收不了。
30. **菜单不能替用户选**。给出选项、代价和耗时实情，等用户定；用户说"你定"才自己选并说明理由。实测最危险的做法是拿 2:1 的票数去压作者直觉（投票会把方案推向"信息更全"，而创作类的 KPI 不是信息完整）。

## 附：两个反直觉的观察

**投票会把方案推向"信息更全"，但创作类的 KPI 不是信息完整**（是点击、是追读、是好看）。所以：

- 投票适合**判断题**（要不要改、选哪个方案、哪条规则更自洽）；
- 投票**不适合**润色题（文案、简介、诗）——这类要让作者直觉优先，会可以开，但结论只作参考。
- 一句话：**会用来解决分歧，不用来追求完备。**

**交叉质询只在真有分歧时值钱**。四家措辞不同、结论一致时，第二轮基本是互相复述（实测两席互相回答"无分歧／没被说服"）——这种情况直接汇总，别把第二轮当依据。
