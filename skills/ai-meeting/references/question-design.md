# 问题单写法 ＋ 六类会议模板

## 通用原则

1. **自包含**：`context: "fresh"` 的席位没有任何上下文。作品背景、机制契约、待审材料全部内联或给出可 `read` 的绝对路径。
2. **逼具体**：不要问"这样好吗"，要问"从第几章开始崩、崩在哪、怎么修"。
3. **给机制契约**：把设定逐条列出（"界壁只放行物不放行读""名额只管升境与出力"）。不列契约，它们会重复我已经犯过的错。
4. **允许反驳我**：写"以下是主持人的判断，**你可以直接反驳，认为他错在哪就明说**"。但**只在需要被反驳时才放我的分析**；要独立判断就不要放（放了会被锚定）。
5. **允许它们自己写一版**（选项 D）。实测多次出现：它们自写的版本比主持人给的候选都好。
6. **给「不确定就写无」的出口**："如果你认为没有，就直接说没有——不要为了交卷硬凑。" 否则它们会编问题。
7. **要求引用原文条款**：验收类会议必须"引用改后的原文作为依据，不许凭印象"。
8. **字数写成"左右"**：绝不写"精确 N 字"（会触发数字数回路）。
9. **强制结尾格式——每席最后一行必须是 `【结论】<一句话主张>`**，并写明"这是硬格式，后面不要再加任何内容"。
   实测两个模型（含最忽略形式约束的那个）都照做了；脚本会从这一行自动抽出 `stance`，汇总时直接用来聚类方向。抓不到时才回读原文。
   一句话主张要求写成**可执行差异**（"改成什么、代价是什么"），不写"更合理些"这类无法聚类的空话。
10. **禁止 harness 报告块**：问题单里明说"不要输出 `acceptance-report` 之类的报告块，也不要包一层 JSON，只写你的判断"。实测有供应商网关会自己塞一段 `acceptance-report` 的 JSON 到回答开头，它会把答案长度灌大、污染第二轮互喂——脚本会剥掉开头的这种块，但从源头减少更好。

## 六类会议

| 类型 | 用来做什么 | 关键问法 |
|---|---|---|
| **① 表态** | 第一次问一个问题 | 每条给理由 + 最大风险 + **什么证据会让你改主意** |
| **② 交叉质询** | 第一轮出现实质分歧 | 匿名喂别家答案；要求"逐条表态 + 你被说服了什么 + 修订后的结论"；明说"别人的设定更能立住就直接承认，不要保面子硬撑" |
| **③ 验收／复核** | 改完一轮后 | 逐条判断"已堵住 / 只堵一半 / 没堵住"，**必须引用改后原文**；再问"这轮改动新引入了什么矛盾"，并给"没有就说没有"的出口 |
| **④ 投票** | 3–5 个互斥方案选一 | 各投一票 + 一行理由 + **"如果我这票是少数，我接受哪个"**；选项一律匿名，不告诉谁提的 |
| **⑤ 创意生成** | 起名、写诗、写文案、设计人设 | 给真实范例定形式（如"《蛊真人》定场诗：4/6/8 句皆可、七言为主、只在情绪顶点念"）；给硬要求（如"主角与女主两首必须互为对偶、末句各自嵌名"）；给禁令（如"不许写成豪言，他们是低境小人物"） |
| **⑥ 机制挑错** | 设定体系防崩 | "找出真实存在的冲突、推导不出的地方、读者会拍桌子的『这也行？』"；"指出最容易被作者自己破坏的三处——写起来最爽但违反守恒的情节冲动" |

对应脚本参数（`references/meeting.js`）：② 和 ⑥ 用 `cross: true`（第一轮表态 + 第二轮匿名互评一次跑完）；①③④⑤ 用 `cross: false`，需要互评时另开一场会喂进选项／改后原文。

## 输出格式模板（投票轮）

```
一、甲／乙／丙／丁（若选丁，写出你的完整版本）｜理由：一行｜少数时我接受：X
二、…
三、如果作者只能记住一条执行纪律，那是什么（一句话）
【结论】<你的一句话主张，可执行差异，不是"更合理些">
```

固定格式有两个好处：票能直接统计；"少数时我接受"让 2:1:1 的分散票当场收敛。最后那行 `【结论】` 是**所有会议的硬要求**（不只投票轮），它是我聚类方向的输入。

## 汇总规则（对主持人）

顺序固定：**票型 → 三类分 → 下一步菜单**。

### 一、票型图（先说清统一还是未统一）

- 未统一时列 A/B/C，每方向写「票数 ＋ 席名 ＋ 一句话主张（＋代价）」。模板在 `SKILL.md` 的流程第 ③ 步。
- **聚类按可执行差异，不按措辞**。两家都说"加强约束"但一家要改机制、一家只加例外条款，那是两个方向。
- **一票的方向也要列**，别只报多数；少数意见往往是最有信息量的。
- **四家四说时不要硬凑方向**：直接说"问题本身没收敛"，并建议重写问题单（通常是问法太宽）。
- 统一时也要单列唯一反对者（如果存在），并说明它的反对理由。
- 分歧的**实质**要说出来（争的是改动幅度？是代价归属？还是信息量不够？）——"C 不是第三个方向，是保留意见"这种区分比票数本身有用。

### 二、三类分

- 分三类：**真洞 / 已知取舍 / 空话**。
- **逐条回读原文验证**，不当传声筒（实测我夸过的一条被三家联合否掉，理由我没想 到）。
- 单列"**谁改了什么主意**"——改判点是最有信号的部分。
- 意见与作者直觉冲突时：**先按作者直觉改稿看效果，不要用投票压过去**（简介那轮我压错过一次）。

### 三、下一步菜单

见 `SKILL.md` 流程第 ④ 步。三条铁律：

1. **菜单是给用户的，我不选**；用户说"你定"才自己选并说明理由。
2. **最多两轮**（表态 + 收敛）。仍然分裂就停，把分歧与各自代价摆给用户拍板——开会不是为了"开到统一"。
3. 选项要**带代价和耗时实情**（"需再花 4 席×2 轮，且 grok 本轮垫底"），不只写动作名。
